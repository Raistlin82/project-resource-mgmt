### [P1/logic] transferDummyMonth adds hours to the target and removes them from the dummy as two untransacted writes per date, so a mid-loop failure double-books the hours and the retry reports "no capacity"

- **where:** `src/server.ts:2952` — also `src/app/services/substitution.util.ts`, `src/db/repositories.ts`
- **failure:** resource-manager POSTs /assignment-months/<dummy 2026-09 row>/substitute with targetResourceId = Marco (8h/day cap, nothing booked). The dummy holds 8h on each of 20 working days. On date #5 the `repos.assignmentDays.remove(dummyDayId)` write fails (transient Postgres error, or the worker is restarted mid-request). State left behind: dates 1-4 moved correctly, date #5 exists TWICE — 8h on Marco's row AND 8h still on the dummy's row — dates 6-20 still on the dummy. `recomputeAssignedHours` never ran (it is after the loop, line 2982), so both assignments' `assignedHours` are stale too. The caller gets 200 with a soft 'failed unexpectedly' note. The aggregates then recompute from `assignmentDays` (recomputeResourceUtilization :1376, recomputeRequestStaffing :1407), so Marco's utilization now counts 8h he never received and the /schedule and /capacity screens show the same 8h twice. Retrying the substitution does NOT heal it and misstates the reason: `planSubstitution` (src/app/services/substitution.util.ts:57-59) computes `room = cap - booked` = 8 - 8 = 0 for date #5, so it moves nothing and `transferDummyMonth` returns `skipped: 'the target has no capacity left in this month'` (src/server.ts:2998) — the operator is told Marco is full when what fills him is a phantom copy of the dummy's own hours.
- **fix:** Wrap the locked write section in `withRepositoriesTransaction` (already imported at src/server.ts:7) and issue the day-row writes, `recomputeAssignedHours` and `syncSubstitutionBooking` through its `transactionRepos` — `recomputeAssignedHours` already takes a `repositorySet` parameter (src/server.ts:2584-2590); `syncSubstitutionBooking` (:2825) needs the same parameter added. Keep the two `res:` locks outside it, as PUT /assignments/:id/allocation does. Because `withRepositoriesTransaction` is a pass-through on the in-memory adapter (src/db/repositories.ts:552), also track the dates already applied and, on failure, subtract what was added to the target and restore what was taken from the dummy — the same compensating-undo `generateBillingInvoice` performs in its catch.
- **detector:** Extract the per-date move into a testable seam (e.g. `applySubstitutionDays(deps, plan, dummyAssignmentId, targetAssignmentId)` in a new src/server/substitution-write.util.ts) and add a spec in the exact style of src/server/commercial-write.util.spec.ts:37, whose `assignmentDays.remove` rejects on the second date. RED assertion: `expect(sumHours(dummyRows) + sumHours(targetRows)).toBe(preTotal)` — today it equals preTotal + 8. Non-vacuous because the load-bearing half is an ASSERTION OF ABSENCE: `expect(await days.get(`${targetId}:${failDate}`)).toBeUndefined()`. A test that only asserts 'the dummy still holds its 8h' is GREEN on today's bug (the dummy does still hold it); only 'the target holds no copy' is red. Add the retry half — after the compensated failure, a second call must report `transferredHours` equal to the full month total — which today returns 0 with 'the target has no capacity left in this month'.

### [P2/api] The >50000 escalation is decided from a client-declared `amount` that is never reconciled with refId, so a requester chooses their own approval chain

- **where:** `src/server.ts:5821` — also `src/db/seed.ts`, `src/app/approvals/approvals.ts`
